Change data capture

A committed change reaches Redis

MySQL commits first. Debezium captures its binlog change, Kafka keeps the event, and Flink updates Redis.

Kafka keeps changes while a consumer catches up

Kafka retains events while Flink pauses. Flink catches up in partition order; a version check at the Redis sink makes replays harmless.

One delete can trigger cleanup in other services

CDC and Flink turn deletes into purge events. Each service removes its own records, producing the next round of changes.

Model and source notes

These are illustrative animations, not a running CDC deployment. The first two figures use MySQL → Debezium → Kafka → Flink → Redis. The original post’s online-to-offline ETL is represented by the same change propagation pattern, with Redis as the derived store. The cleanup figure preserves service-owned records and abstracts capture, Flink routing, and Kafka purge topics into the connecting paths. It does not depict automatic foreign-key cascades.

Debezium reads MySQL’s row-based binlog after an initial snapshot. Binlog positions and Kafka offsets are separate coordinates. Ordering here is within one Kafka partition. The recovery example uses an atomic version check plus update at the Redis sink; a Flink checkpoint alone does not provide exactly-once Redis side effects. Deletions require equivalent replay protection, including a retained deletion version, if stale updates can arrive.
