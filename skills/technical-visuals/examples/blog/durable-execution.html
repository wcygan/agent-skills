Durable execution

A workflow runs activities in order

Reserve a seat, charge the card, then send a receipt. A failed payment retries before the workflow moves on.

Tasks wait until a worker picks them up

Temporal queues a Reserve seat activity for each booking. A worker takes a task, calls the seat service, and reports the result to Temporal. Temporal records that result in MySQL.

Replay starts at the beginning of history

Workers poll Temporal for tasks. Workflow code reuses saved results and requests the receipt activity. Activity code sends it and reports completion; a later workflow task brings back the saved result.

The same retry can produce two different outcomes

A crash before completion is recorded can trigger a retry. The idempotency check returns the saved receipt instead of charging again.

Model and sources

Task deliveries are responses to worker long polls. The animation shows one poll before each response; real workers keep pollers running concurrently. This shows regular activity dispatch rather than eager execution or local activities.

Replay shows selected completed events, not the full event history. The worker reruns workflow code and matches its commands to history; completed activity results are reused. The payment comparison shows two alternative provider implementations.

Temporal: activity idempotency

MySQL is the Temporal Service’s persistence backend; workers communicate with Temporal, not its database. The queue shows ready Activity Tasks from three independent workflows, not three simultaneously ready steps of one sequential workflow. Slots show occupancy, not a configured queue capacity. History rows summarize selected events; timing is illustrative.

Activity retries follow a configured retry policy. The payment example assumes that the provider enforces a stable idempotency key. Workflow replay rebuilds state from history; it does not replay completed external side effects.
