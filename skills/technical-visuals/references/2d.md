# 2D playbooks

Read only the matching branch. Start with the reader's question and an evidence-backed
model, then choose the fewest marks needed to answer it.

## Architecture and routing

Use when the reader asks what connects to what, which owner handles a request,
or what changed in a dependency. Trace nodes and edges from the source. Establish
one arrow meaning, group by actual ownership, and highlight the relevant route.
Use Mermaid when automatic layout and native Markdown are enough; use SVG when
port placement, semantic shapes, or visual hierarchy require control. For a native
Markdown figure, read the [Mermaid example](mermaid.md).

Good: client → router → two labeled workers, with one selected path.
Bad: equal emphasis on every box, repeated technology logos, unlabeled lines.
Repair: label edge verbs, remove irrelevant neighbors, and preserve the important
fanout. Never remove an edge that changes the system's meaning.

Group a leader and its replicas visibly when that local relationship explains a
quorum. Shrink or rearrange their shapes to create space before removing actors.
Use the shortest clear orthogonal route to the actual port; payloads follow the
same route as the connector.

## State, sequence, and recovery

Use numbered frames for what happens next. Name the initial condition and the
transition; show the result and any material failure branch. Use a stepper when
readers benefit from changing state. Keep geometry stable between steps so movement
does not masquerade as a domain event. Supply a reset that restores the initial state.

Good: checkpoint 42 → crash → restore 42 → replay records after 42.
Bad: animated dots with no named checkpoint, ordering, or restoration boundary.
Repair: turn decorative motion into discrete, labeled state changes.

Show accumulated state while messages arrive: vote pips, received record chips,
or a small count can explain progress without a metadata table. Update recipients
on arrival. For a multi-stage process, a segmented rectangle can retain completed
stages in green while the next stage is pending; reset it only on replay. Keep
completion distinct from a successful outcome, especially when the process aborts.
Use one progress segment per visually perceptible transition, rather than exposing
bookkeeping states that look identical. Combine contiguous protocol phases into
one explanation when the same actors and geometry carry the story; mark phase
completion without resetting the accumulated progress.

## Bounded capacity and ordered records

For queues, distinguish waiting, active, accepted, and rejected work. Show finite
slots when capacity is bounded, and identify what happens at the limit. For logs,
show offsets and a read position; do not imply that removing a visible record is
how log consumption works. Clearly label simplified toy models.

Good: three of four queue slots occupied; a selected next job; two active workers.
Bad: a pile of glowing tokens with no capacity or state labels.
Repair: give each repeated mark a semantic role and pair color with words or numbers.

Receiving and applying are separate states. Show records traveling into a replica's
buffer before it changes its applied state. Several records may arrive or wait while
one active record applies in a serial-applier teaching model; do not imply that all
buffered records apply together. State that model's scope rather than making a
universal claim about database execution.

## Capacity, proportions, and traffic

Use an icon, a short value, and a proportional bar for each resource budget.
Keep the denominator clear: a pool's share of stored data and its page-hit rate
are different quantities, even when paired gauges make their contrast useful.
Do not draw per-core activity from aggregate CPU utilization. Preserve units and
qualifiers; a rounded estimate or an illustrative daily curve is not telemetry.
Keep the measured/illustrative distinction visible when supporting prose is collapsed.

For query traffic, let the moving cursor, current rate, and compact query-mix and
latency values carry the lesson. Distinguish an average from tail latency and page
hits from whole-query hits. On phones, stack resource cards and reflow charts;
do not shrink the desktop composition until labels become decoration.

## Before/after and PR figures

Use identical scale, labels, and framing across versions. Name the behavior change
rather than duplicating the diff. A tiny change can use one annotated diagram with
the affected path highlighted. Use real screenshots when claiming actual UI behavior;
a conceptual mockup must be labeled as such.

Good: same cache topology, with hit and miss routes distinguished by selected state.
Bad: before and after differ in layout, theme, and data, making the actual change unclear.
Repair: hold presentation constant; vary only the behavior under discussion.

## Measured comparisons

Choose a chart according to the question: bars for category comparison, lines for
change over ordered time, distributions for spread. Include units, sample scope,
and uncertainty when available. Use a common baseline for comparable bar lengths;
explain any clipped axis. Keep measured and illustrative numbers distinct.

Good: latency before/after with workload, units, sample count, and spread.
Bad: invented percentages, 3D bars, a truncated scale exaggerating a small difference.
Repair: return to the source data and choose an honest encoding. The topology
examples are not chart templates; use a suitable plotting library for real data.

## Acceptance

At the intended viewing width, readers can identify the actors, arrow meaning,
key change, and boundary without hovering. Check all named states, both supported
themes, route attachment, label collisions, and the static export. For data, verify
the plotted values and transformations against the source, not just the screenshot.


For animated reading demos, Reset or Replay restores the starting model and resumes
playback when visible. It overrides an earlier manual pause. Keep reduced-motion
preferences paused and retain pause/step as explicit inspection controls. Verify a
reset after pausing, rather than testing reset only while already playing.
