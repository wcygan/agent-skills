# Pull request design system

Make the review decision easy: what changes, why it matters, and what was observed.
Use the [example gallery](../examples/pull-requests/index.html) for the presentation
pattern and [prepare-pull-request](../../prepare-pull-request/SKILL.md) for the
publication workflow. The examples are fictional; their evidence is not a test result.

## Synthesize the change before drawing

1. Read the final diff against its intended base, relevant callers, and tests.
   Identify the concrete failure or need, the changed behavior, and what stays true.
2. Trace one representative request or interaction. Keep only actors, decisions,
   state transitions, and terminal outcomes needed to explain the difference.
   Code is the source of facts, not the required level of diagram detail.
3. Write one short problem/result paragraph. Choose the visual form that reveals
   the mechanism: service paths for cache lookup, form state for retry, or occupied
   capacity for queue admission. Keep component silhouettes and identities stable.
4. Choose the distinct scenarios needed to establish the claim, including relevant
   failure and recovery paths. Pair each visible scenario figure with a collapsed
   transcript of actual commands, responses, logs, or UI interactions and results.
5. Check every statement against the current revision and evidence. Remove repeated
   explanations and incidental implementation detail; retain important limits.
   The examples are fictional, so never copy their output as evidence of a real run.

Start with the editable [cache](../examples/pull-requests/cache.md),
[form retry](../examples/pull-requests/retry.md), or
[queue](../examples/pull-requests/queue.md) body and its adjacent SVG assets.
The [gallery](../examples/pull-requests/index.html) previews the GitHub-rendered
Markdown. Adapt the closest pattern; do not force unrelated changes into its topology.

## One change a reviewer can hold in mind

Aim for **300 changed lines or fewer** as this user's default, not a universal
quality threshold. Count additions plus deletions against the intended PR base,
including tests and documentation. Show generated files, lockfiles, and mechanical
churn separately when material, while retaining the honest raw total. Binary assets
need explicit review even though they have no line count. Never report net growth
as review size or compress code to meet the target.

Above the target, reconsider the boundary. Separate unrelated cleanup, or stage
independent behaviors as working increments. Keep implementation with its relevant
tests. Explain a cohesive exception in one sentence; do not split into broken
intermediate states, unused abstractions, or a PR of implementation followed by
its tests. For dependent PRs, state the dependency and intended review order.

## The reading order

Use a concise PR title and exactly two top-level body sections:

```markdown
## Problem & Solution Overview

Describe the problem and resulting behavior in one short paragraph.
Include a compact visual when it clarifies the change.

## Testing Done

State what ran, what was observed, and material limits.
```

Place any supporting headings beneath these as `###` subsections. Keep risks
visible; put long commands or traces in a named disclosure or durable link under
Testing Done. Follow a required repository template when it overrides this default.
Omit conversational history, file-by-file narration, and repeated summaries.

## Choose the smallest useful visual

Design the visual around the mechanism, not a reusable row of text boxes. A cache
change needs branching and a store; draft retention needs visible field state;
backpressure needs occupied capacity and admission. Do not force the same shapes,
colors, or before/after layout onto unrelated changes. Reuse the shape vocabulary:
client screen, service rectangle, cache memory module with pins, database cylinder,
and capsule response codes. Keep each component's silhouette and category color
consistent between the overview and scenario diagrams; storage stays blue even
when a request succeeds. Reserve green/red for outcomes, not component identity.
UI form fields and buttons should retain their UI shapes.

Use one overview figure in Problem & Solution Overview. Under Testing Done,
organize meaningful scenarios as subsections, each starting with a visible diagram.
Keep commands, responses, and logs in a collapsed GitHub `<details>` block labeled
“Commands and results”; place common setup in its own disclosure. Keep the scenario
outcome and any material caveats readable without expanding transcripts.

The gallery ships actual `.md` bodies and standalone SVGs. Its body previews are
generated by GitHub’s Markdown API; gallery controls are not part of the PR.
Upload the image and replace the relative path with an accessible attachment URL
when pasting a body into a PR. No custom CSS, inline SVG, or JavaScript is required
in the published description. Set an explicit image width in GitHub-supported HTML
(e.g. `<img src="..." alt="..." width="448">`) so a diagram supports the prose
instead of dominating the page. Prefer a shallow, horizontal flow that uses the PR
content width; use narrower images for naturally vertical subjects. Keep labels readable at that size and on mobile;
redraw a dense diagram rather than shrinking it until its labels are illegible.

| Reviewer question | Use | What it establishes |
| --- | --- | --- |
| What path or responsibility changes? | Small Mermaid flow or labeled SVG/PNG | Conceptual explanation |
| What will a person see? | Actual before/after application screenshots | Rendered states in that environment |
| Does the interaction work? | Short recording or trace with observed result | The exercised sequence |
| Is performance different? | Measured chart with workload, units, and spread | The measured comparison only |

Prefer 3–6 actors, short labels, stable colors, and one clear reading direction.
Use the technical-visuals tokens for custom assets. For GitHub Mermaid, prefer its
native theme adaptation over hardcoded light-only fills. Export a readable static
frame when a local animation explains the change; interactive HTML/JavaScript does
not run inside a PR description. A link to an interactive demo is supplementary.
A typo or straightforward dependency pin may need no diagram.

## Evidence that another person can follow

Capture the **current revision**, relevant **environment**, **launch command**,
**action**, and **observed result**. Add focused test commands and their outcomes.
Tie an artifact to that same revision; rerun affected checks after code changes.
For example, an honest unfilled record is:

```text
Revision: <head SHA>; environment: <browser / database / relevant configuration>.
Started: <command>.
Exercised: <changed interaction or request, including the relevant failure path>.
Observed: <specific visible response and persisted state, where relevant>.
Checks: <command → actual result>. Limits: <material untested case>.
```

Compress the completed record into a sentence or two; do not leave placeholders
in a ready-for-review PR. If execution is blocked, say “Not run” and name the blocker;
label suggested commands as proposed. A screenshot cannot prove persistence, a
conceptual diagram cannot prove execution, and a passing suite is not proof of
all production conditions. Avoid dumping entire logs into the description.

## GitHub delivery

Use a fenced `mermaid` block for a small flow, or a durable image attachment with
alt text and a factual caption. Verify the rendered result and reviewer access.
Never paste localhost, `file://`, or machine-local image paths into a published PR.
Keep editable source where repository conventions expect it. Use compatible video
for timing-sensitive evidence and retain a text summary of the result.

GitHub supports `<details>` for optional commands and traces. Do not collapse the
main outcome or a known failure. Attachments upload before a comment is submitted;
public-repository attachments can be public. Remove secrets and private test data
before uploading. Check current GitHub documentation for format/size limits and
installed `gh` help before depending on CLI attachment flags.

## Review before requesting review

Read the final diff against its actual base. Confirm one purpose, relevant tests,
current evidence, working links, legibility in both themes, and any required CI or
repository gates. A reviewer should be able to explain the change without opening
every file, then use the code and evidence to challenge it. The gallery is an aid
to that review, not an automatic safety score.

## Sources and policy boundaries

Reviewed 2026-10-15. The 300-line target, visual-first house style, and evidence
record above are our synthesis and user preferences. They are not GitHub rules.

- [Google: small changes](https://google.github.io/eng-practices/review/developer/small-cls.html)
  supports coherent scope, related tests, and working intermediate changes.
- [Google: descriptions](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)
  supports standalone context, what/why, and updating the description as scope changes.
- [GitHub: helping reviewers](https://docs.github.com/en/pull-requests/concepts/helping-others-review-your-changes)
  supports focused changes, context, and self-review.
- [GitHub: diagrams](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams),
  [attachments](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files),
  and [disclosures](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-collapsed-sections)
  describe supported presentation mechanisms.
- [Playwright: best practices](https://playwright.dev/docs/best-practices) and
  [trace viewer](https://playwright.dev/docs/trace-viewer) support user-visible checks
  and inspectable interaction evidence.

```sh
PLAYWRIGHT_MODULE=/absolute/path/to/playwright/index.mjs \
  node skills/technical-visuals/scripts/check-pull-requests.mjs /tmp/pr-gallery-check
```

This checks the gallery itself: specimen selection, evidence labels, themes, phone
label size and overflow, and the downloaded template. It does not run the fictional
applications described by the specimens.

Regenerate the bundled body previews after editing their Markdown with
`node skills/technical-visuals/scripts/render-pull-requests.mjs` (authenticated `gh`).
This renders fictional text through GitHub’s API; it does not create a PR.
