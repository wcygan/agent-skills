Service capacity
Three stateless Frontend instances receive application RPCs through a gRPC load balancer. History owns workflow state; Matching distributes named task queue partitions. SDK workers run your Workflow and Activity code outside the server.

    
Persistence capacity
Each MySQL cylinder includes its own VTTablet. Each example write shard has one primary and two replicas; replicas provide redundancy. Resharding represents the topology after copying data, catching up replication, and switching traffic; it does not simulate that migration.

  

  
Illustrative counts, not sizing recommendations. Logical History Shard count is fixed after initialization. This view shows workflow data paths; Frontend metadata access, visibility, the server’s internal Worker Service, and Vitess control-plane components are omitted.

  
Vitess is an optional integration. Temporal’s persistence documentation states that its compatibility tests do not cover Vitess. The 2022 PlanetScale deployment is a customer-specific example. Validate the deployed Temporal schema, table routing, transaction locality, and database versions before using this layout in production.
