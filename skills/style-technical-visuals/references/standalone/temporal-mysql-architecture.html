An illustrative production topology. Twelve logical History Shards are fixed; service replicas, worker capacity, and physical database partitions can change separately.





Database replicas provide redundancy rather than additional independent write shards. Resharding requires data copying, replication/catch-up, and a controlled traffic switch; the button illustrates the resulting topology, not the migration protocol. Production configuration must validate schema, transaction locality, and version compatibility. Counts shown here are examples, not sizing recommendations.


Further reading: scaling Temporal


Service replicas, logical History Shards, and physical database shards are separate scaling dimensions. The current scene shows the minimal architecture; these sources explain how to expand it.


    

  • Temporal: Scaling Temporal — The basics (2023). Load-test, measure, and tune History resources, shard contention, worker polling, and persistence capacity. Track state-transition throughput alongside request and schedule-to-start latency. Example tuning values are workload-specific.
    • 

  • Temporal Server documentation. Frontend is stateless; History, Matching, and the internal Worker Service scale independently. History processes can change in number while ownership of existing logical shards redistributes; the configured History Shard count is fixed after initialization. Application SDK workers remain separate from the internal Worker Service.
    • 

  • PlanetScale: Temporal Workflows at scale — Part 1 (2022). Introduces persistence responsibilities and Vitess over MySQL as a way to horizontally partition SQL storage. For an open-source deployment, the architectural building blocks are Vitess and MySQL.
    • 

  • PlanetScale: Temporal workflows at scale — Part 2, Sharding in production (2022). Explains VTGate routing, VSchema/Vindexes, and a customer-specific mix of sharded and unsharded keyspaces, with table placement using keys such as shard_id and range_hash. Validate table placement and transaction requirements against the deployed Temporal schema; this historical example is not a universal configuration.
    • 



Diagram takeaway: show independently scalable service pools, external application workers, and a separate Vitess/MySQL persistence layer. Many logical History Shards can map to fewer physical database shards. Rebalancing History ownership and resharding stored data should be illustrated as different operations.




The layout follows the official Matching context and workflow lifecycle diagrams. The animation follows one simplified Workflow Task, not a full Activity lifecycle. Persistence writes represent logical durability boundaries rather than every SQL transaction. Visibility and the server’s internal background Worker Service are intentionally omitted from this diagram, as are replication, service scaling, retries, and authentication. A deployed server still needs release-appropriate configuration and schemas; this is not an installation recipe.
