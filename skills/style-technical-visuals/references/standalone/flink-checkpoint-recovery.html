Real database sink patterns

PostgreSQL: ignore an event that was already written

This minimal SQL example matches the animation. A custom Flink JDBC sink can bind the stable event ID and payload into the parameterized INSERT. The primary key is enforced by PostgreSQL; the same ID arriving again creates no additional row. This is an example statement, not a running database connection.

CREATE TABLE processed_events (
  event_id BIGINT PRIMARY KEY,
  payload TEXT NOT NULL
);

-- SQL supplied to a JDBC prepared statement:
INSERT INTO processed_events (event_id, payload)
VALUES (?, ?)
ON CONFLICT (event_id) DO NOTHING;

Use a globally stable ID for each logical event. This pattern suits immutable events: reusing an ID with a different payload keeps the original row. If a separate business update is needed, commit its effect and the deduplication record in the same database transaction. PostgreSQL: ON CONFLICT reference and examples.

Flink SQL JDBC: idempotent upserts for PostgreSQL or MySQL

Flink’s JDBC table sink uses primary-key upserts. PostgreSQL uses ON CONFLICT DO UPDATE; MySQL uses ON DUPLICATE KEY UPDATE. Reapplying the same row values preserves the same result. This differs from the demo’s insert-and-ignore policy. Declare the key in Flink and enforce it in the actual database; version checks are needed if older updates can overwrite newer values. Official JDBC idempotent-write explanation and MySQL table configuration example. Check connector compatibility for the Flink release you use.

Alternative: checkpoint-coordinated XA transactions

Flink’s DataStream JDBC exactly-once sink uses XA transactions instead of duplicate suppression. Its documentation includes PostgreSQL and MySQL data-source examples, per-transaction connections, and database configuration requirements. It also requires disabling JDBC execution retries for the documented guarantee. This is a separate approach from the sink animated above.
