# 3D Technical Diagrams and Visualizations

Use `standalone-3d/` as the primary foundation. Read the closest example's source
before adapting its world geometry, projection, camera, tokens, or interaction.
These references project world coordinates into SVG; 3D does not require a
new rendering dependency. Choose a different renderer only when the requested
artifact needs capabilities the reference approach cannot provide.

## Preserve the visual language

Preserve existing product tokens; otherwise copy the chosen example's shared
dark `:root` block. The fallback uses `#111111` canvas, `#1c1c1c` panels,
`#fafafa` text, and sparse `#f35815` emphasis. Use its semantic border, muted
text, success, warning, failure, and information roles consistently.

Use mono-forward labels and controls, tabular metrics, thin outlines, and direct
labels. Keep labels upright and legible as the scene rotates. Combine color
with labels, shape, or position. Depth should explain grouping or topology;
retain a readable initial view and captions that explain the relationships.
If another theme is required, verify its contrast and separation independently.

## Model once, project consistently

Store semantic nodes, face-center ports, and ordered routes in world space.
Derive wires, arrowheads, and packet positions from the same routes and project
them through the same camera. Cache route lengths until the route changes.
Use the selected example's projection and camera conventions together rather
than mixing independently calculated screen positions.

Keep source and destination ports attached to actual surfaces. Verify route
clearance in world space and label separation in screen space. Use depth ordering
for faces, but do not assume one average-depth key can correctly order a long
connector against every surface. Where a connector crosses depth boundaries,
use surface-aware clipping or segmentation.

Keep active-route visibility separate from packet occlusion. Calculate static
baseline cutouts when the route or camera changes. A moving packet's visibility
must follow the projected surfaces it passes behind. Bound moving masks to the
glyph plus stroke padding and reject unrelated surfaces by bounds before clipping;
avoid scene-sized moving masks on many connector fragments.

Geometry is complete when full orbit preserves attached ports, visible
camera-facing stems, correct arrowheads, readable labels, and front/rear occlusion.

## Keep rendering proportional to change

Separate construction from animation. Retain unchanged SVG nodes while an
existing packet moves; update its position and bounded visibility data only.
Do not rebuild an unchanged topology on every animation frame.

| Event | Work |
| --- | --- |
| Initial load or topology change | Create or update nodes, routes, ports, and labels |
| Phase or selection change | Update affected state and active route |
| Camera orbit | Reproject and recompute depth visibility once per frame |
| Packet movement | Update retained packet geometry and local visibility |
| Zoom | Update the camera or `viewBox` when projection permits |
| Paused, hidden, or offscreen | Suspend automatic animation scheduling |

New jobs or records may allocate elements when those events occur. If topology
itself animates, define its update budget explicitly. Avoid unchanged attribute
and status-text writes. Coalesce pointer events into the latest camera state
and request at most one render per display frame.

Track playback intent separately from scene and document visibility. Cancel
automatic callbacks when playback cannot advance, and reset the elapsed-time
clock on resume. Paused users can still orbit, zoom, or step through bounded
input-driven updates without restarting automatic playback.

## Make camera and playback accessible

Adapt the selected example's orbit, zoom, and reset controls to the artifact.
Preserve pointer capture and recovery after capture loss. Provide keyboard
camera controls, visible focus, and a stable viewport as zoom changes. Keep
camera interaction independent from simulation playback.

Give simulations pause, step, and reset controls when relevant. Start automatic
motion only when reduced motion permits; respond to preference changes and keep
static relationships and discrete steps available. Check actual SVG and scripted
animation, since CSS alone does not disable them. Allow normal page scrolling
and responsive control wrapping; do not impose gallery embedding protocols.

## Verify and deliver

Check supported viewports and themes, all phases and controls, several camera
angles, both orbit directions, zoom limits, reset, and pointer capture loss.
Inspect actual browser pixels for label collisions, port attachment, active-route
overlap, arrowhead arrivals, and payloads passing behind nodes.

For animated topology-and-payload scenes, also verify:

- Existing scene and packet nodes retain identity during steady playback;
  moving a packet creates zero SVG elements and replaces no complete scene.
  Set a bounded attribute-write budget for the chosen glyph.
- Rebuilds correspond to phase, topology, or view changes rather than packet
  ticks. A burst of pointer events produces at most one rebuild per frame.
- After pending input settles, pause, hidden-tab, and offscreen states stop
  automatic callbacks and DOM writes. Resume preserves playback intent without
  a time jump; reduced-motion startup does not start automatic motion.
- Shared and reversed routes, full playback cycles, and occlusion work at
  multiple angles. Use independent geometry checks where available and browser
  inspection for antialias boundaries.

Measure performance under equivalent scene, phase, camera, duration, warm-up,
and runtime conditions. Separate steady playback from phase transitions and
orbit. Script/DOM operation counts do not establish browser frame rate, paint,
GPU cost, or power consumption. State missing visual or performance evidence.
