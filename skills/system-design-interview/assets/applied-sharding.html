Sharding

Which database owns the rows?

Database context

Context: MySQL 8.4 / InnoDB behind Vitess VTGate. SQL is illustrative: production queries use bound parameters and authorize the caller’s tenant or resource. Vitess VTGate chooses a shard using the VSchema primary vindex; MySQL chooses partitions and local indexes. Verify the actual plan with EXPLAIN.

Illustrative screen · sample records

How it works API · SQL · design choices

Database workload: Read one team’s latest events; append team events. One DB has reached its write budget.

1 · API request
GET /teams/42/events

Path parameters:
  tenant_id: 42

Query parameters:
  limit: 50
2 · Vitess routing

Primary vindex column: tenant_id. Type: hash. Equality on this column lets VTGate target its owning shard; absent a usable vindex, queries may scatter.

3 · SQL submitted to Vitess VTGate
Illustrative SQL
SELECT
  * 
FROM events 
WHERE tenant_id = 42 
ORDER BY
  created_at DESC,
  event_id DESC 
LIMIT 50;
Vitess routing configuration
Vitess VSchema · primary vindex
{
  "sharded": true,
  "vindexes": {
    "tenant_hash": {
      "type": "hash"
    }
  },
  "tables": {
    "events": {
      "column_vindexes": [
        {
          "column": "tenant_id",
          "name": "tenant_hash"
        }
      ]
    }
  }
}

VTGate reads tenant_id from the SQL predicate → hash vindex → keyspace ID → shard range → MySQL. The application connects to VTGate. This is an illustrative keyspace VSchema; provision tables and shards separately.

Without tenant-based placement, run this on every shard and merge the latest results.

Write / tradeoff: VTGate routes inserts by tenant_id too. Shared vindexes co-locate a tenant; oversized tenants may still need a different key.

A creation-month shard cannot be inferred from this code without another lookup.

Write / tradeoff: Hash distributes independent inserts. A very popular code still needs caching.

VTGate reads device_id from the SQL predicate → hash vindex → keyspace ID → shard range → MySQL. The application connects to VTGate. This is an illustrative keyspace VSchema; provision tables and shards separately.

A time-based shard puts all current writes together; device routing spreads devices.

Write / tradeoff: Spread devices, then partition by time within each shard. Fleet-wide analytics still fan out.

Implementation notes

Immutable tenant keys simplify routing. Large tenants may need dedicated placement or smaller buckets; smaller buckets increase read fanout. Cross-shard transactions require coordination.
