01 Activity retention

A team member selects March to review that month’s activity.

Team 42 · ActivityProduct view
March 2026
Mar 28Maya uploaded a file
Mar 20Leo joined the team
Mar 12Ana posted an update

Illustrative screen · sample records

How it works API · SQL · design choices

Database workload: Read March events; expire whole months of history. All partitions remain on one DB.

1 · API request
GET /teams/42/events

Path parameters:
  tenant_id: 42

Query parameters:
  from: 2026-03-01
  to: 2026-04-01
2 · Select partitions

Prune: created_at bounds select March; skip January and February.

3 · SQL on the logical table
Illustrative SQL
SELECT
  * 
FROM events 
WHERE tenant_id = 42
  AND created_at >= '2026-03-01'
  AND created_at < '2026-04-01';
MySQL table partition clause · schema excerpt
PARTITION BY RANGE COLUMNS (created_at) (
  PARTITION p_before_march VALUES LESS THAN ('2026-03-01'),
  PARTITION p_march VALUES LESS THAN ('2026-04-01'),
  PARTITION p_future VALUES LESS THAN (MAXVALUE)
)

Expected pruning: p_march. Confirm the EXPLAIN partitions column; this is an expectation, not a captured plan. Every primary/unique key must include created_at; partitioned InnoDB tables cannot use foreign keys.

WHERE event_id = 9001 has no time bound: inspect all retained month partitions.

Write / tradeoff: Create future partitions and handle late events; the current month still shares one DB’s write budget.

Database workload: Read a billing period; archive closed periods under one agreed retention policy.

1 · API request
GET /billing/entries

  period: 2026
2 · Select partitions

Prune: billing_period = 2026 selects that period’s partition.

3 · SQL on the logical table
Illustrative SQL
SELECT
  * 
FROM billing_entries 
WHERE billing_period = 2026;
MySQL table partition clause · schema excerpt
PARTITION BY RANGE (billing_period) (
  PARTITION p_before_2026 VALUES LESS THAN (2026),
  PARTITION p_2026 VALUES LESS THAN (2027),
  PARTITION p_future VALUES LESS THAN MAXVALUE
)

Expected pruning: p_2026. Confirm the EXPLAIN partitions column; this is an expectation, not a captured plan. Every primary/unique key must include billing_period; partitioned InnoDB tables cannot use foreign keys.

Tenant-only partitions mix years: this period query can require every tenant partition.

Write / tradeoff: Align chunks with the billing lifecycle. A tenant partition per customer can create excessive partition counts.

04 Regional records

An operator chooses EU to see records for European customers.

Regional recordsProduct view
Region: EU
BerlinCustomer record #701
ParisCustomer record #705
MadridCustomer record #711

Illustrative screen · sample records

How it works API · SQL · design choices

Database workload: Queries include region; inserts already carry an immutable region code.

1 · API request
GET /records

Query parameters:
  region: EU
2 · Select partitions

Prune: region = EU selects the EU LIST partition.

3 · SQL on the logical table
Illustrative SQL
SELECT
  * 
FROM records 
WHERE region = 'EU';
MySQL table partition clause · schema excerpt
PARTITION BY LIST COLUMNS (region) (
  PARTITION p_eu VALUES IN ('EU'),
  PARTITION p_us VALUES IN ('US')
)

Expected pruning: p_eu. Confirm the EXPLAIN partitions column; this is an expectation, not a captured plan. Every primary/unique key must include region; partitioned InnoDB tables cannot use foreign keys.

LIST partitions must enumerate accepted regions. A new region needs a matching partition before insertion.

HASH(record_id) cannot prune from region alone; examine every hash partition.

Write / tradeoff: Use region only when access patterns fit. These are table pieces on one server, so this alone does not enforce geographic residency.

05 Device time windows

An operator selects a device and a time window to review readings.

Device 8 · ReadingsProduct view
March 1–31
Mar 28Temperature · 21.4 °C
Mar 20Temperature · 21.3 °C
Mar 12Temperature · 21.2 °C

Illustrative screen · sample records

How it works API · SQL · design choices

Database workload: Read one device over a short time window; delete expired telemetry.

1 · API request
GET /devices/8/readings

Path parameters:
  device_id: 8

Query parameters:
  from: 2026-03-01
  to: 2026-04-01
2 · Select partitions

Prune: timestamp bounds select March; a local index then filters device 8.

3 · SQL on the logical table
Illustrative SQL
SELECT
  * 
FROM readings 
WHERE device_id = 8
  AND recorded_at >= '2026-03-01'
  AND recorded_at < '2026-04-01';
MySQL table partition clause · schema excerpt
PARTITION BY RANGE COLUMNS (recorded_at) (
  PARTITION p_before_march VALUES LESS THAN ('2026-03-01'),
  PARTITION p_march VALUES LESS THAN ('2026-04-01'),
  PARTITION p_future VALUES LESS THAN (MAXVALUE)
)

Expected pruning: p_march. Confirm the EXPLAIN partitions column; this is an expectation, not a captured plan. Every primary/unique key must include recorded_at; partitioned InnoDB tables cannot use foreign keys.

A separate partition per device can prune device queries, but millions of partitions are impractical.

Write / tradeoff: Choose practical time chunks. An index inside each chunk can find the device. Partitioning does not itself guarantee fewer row reads.

Implementation notes

MySQL / InnoDB: every unique key must include the partition key, and partitioned tables cannot use foreign keys. Prepare future partitions and handle late arrivals. Retention rules must match month boundaries. Detaching or dropping partitions needs a locking plan. Partitioning within one database does not add server capacity.
