Combining them

Route → prune → seek.

The situation

A growing activity feed needs more write capacity, month-based retention, and fast “latest 50” reads for one team. Each need earns a different tool.

Shard by tenant, partition by time, and index for the feed query. The bad case changes the premise: a small workload already fits one DB.

1 · API request
GET /teams/42/events

Path parameters:
  tenant_id: 42

Query parameters:
  from: 2026-03-01
  to: 2026-04-01
  limit: 50
2 · Vitess route → MySQL prune → B-tree seek

VTGate: hash primary vindex on tenant_id = 42 → owning MySQL shard. March timestamp bounds → March partition. Local tenant/time index → newest rows.

3 · SQL on the selected shard
Illustrative SQL
SELECT
  * 
FROM events 
WHERE tenant_id = 42
  AND created_at >= '2026-03-01'
  AND created_at < '2026-04-01' 
ORDER BY
  created_at DESC,
  event_id DESC 
LIMIT 50;
MySQL local index · secondary B-tree
CREATE INDEX events_feed
ON events (
  tenant_id,
  created_at DESC,
  event_id DESC
);
Vitess routing configuration
Vitess VSchema · routing excerpt
{
  "column_vindexes": [
    {
      "column": "tenant_id",
      "name": "tenant_hash"
    }
  ]
}

Context: MySQL 8.4/InnoDB behind Vitess. tenant_hash is a hash vindex; monthly partitions live inside each shard. This conceptual combination requires validating your Vitess/MySQL version and schema tooling. Bind parameters, authorize the tenant, and verify pruning/index use with EXPLAIN.

Add each layer for a measured need: capacity, retention, or lookup cost.

Implementation notes

Global queries still fan out; hot tenants still need a plan. Transactions and uniqueness are local unless coordinated. MySQL partitioned-table unique constraints include the partition key; partitioned InnoDB tables cannot use foreign keys. Globally unique IDs require a deliberate allocation or tracking strategy.
