FRAMEWORK / WORKED TEMPLATE

URL shortener

A complete example of the five-step interview method.

Question prompt

Design a URL shortener. Users create a short link for a destination URL and open that link to reach the destination. Destinations stay fixed. Custom aliases, analytics, and link editing can wait.

Follow one working request, then add a tool only when a requirement earns it. Numbers below are practice assumptions.

01

Scope

Build two actions and one read guarantee.

WRITECreate a short link

Signed-in creator saves a fixed destination.

READOpen a short link

Anyone follows it to the saved destination.

Out of scope: Analytics · custom aliases · expiry · editing

02

Scale

See the busy period, not just the daily average.

100Mopens / day
1Mcreates / day
≈ 100:1reads : writes
≈ 73 GBlogical records / year*

Reads dominate → start with indexed lookups → measure peak capacity.

Assumptions and arithmetic

100M ÷ 86,400 ≈ 1,157 opens/s. The chart allocates 100M opens across 96 fifteen-minute buckets; one brief burst is 10× the mean. Creates average ≈ 12/s; an assumed 10× peak is ≈ 116/s. *1M creates/day × 200 bytes × 365 ≈ 73 GB before indexes, replicas, and backups. This is synthetic traffic, not live or measured data.

03

Contract and flow

Save before acknowledging; look up before redirecting.

Stored linkaB7x → https://example.com/guideUnique indexed code · fixed destination
Correctness details

Acknowledge only after commit. Store the creator-scoped idempotency result atomically with the link for a defined retry window; reject reuse with a different payload. On a code collision, generate another code within a bounded budget. Read the authoritative store as needed so acknowledged links are immediately readable.

04

Deep dive

Add a cache only when repeated reads earn it.

Measured repeated reads exceed the database budget → add cache-aside.

Cache tradeoffs

Immutable destinations simplify freshness. Avoid caching “not found” in a way that hides just-created links. Bound cold-cache fallback traffic. Replicas and shards need a measured remaining bottleneck and a plan for read consistency.

05

Failure and recovery

Show what the user sees when a dependency fails.

Remaining failure limits

Keep spare capacity for instance failure. A cold cache or popular uncached key can overload the database; use bounded fallback and evaluate request coalescing when measured. Do not acknowledge uncommitted writes. Define acceptable recovery time and data loss before choosing backup and failover mechanisms.

The design in one sentence

A stateless service stores unique immutable links in an indexed database, acknowledges committed creates, and returns redirects; safe retries and bounded fallback protect failure paths.
