1. Infrastructure components

What you put in the architecture.

Relational database

★★★

Related data and transactions.

Tradeoff: Write contention and schema changes.

Details
PostgreSQL · MySQL

Use: Structured data + transactions

Store related records → query and update them together

Cost: Schema changes and write contention need care.

Cache

★★★

Reuse frequently read data.

Tradeoff: Stale values and bursts of misses.

Details
Redis · Memcached

Use: Fast access to repeated data

Cache-aside → check cache, then database
Expiration → remove old entries

Cost: Stale data; bursts of cache misses.

Related: Caching strategies

Search index

★★★

Find and rank matching documents.

Tradeoff: Extra storage; results may lag updates.

Details

A searchable representation of documents optimized for text queries, filters, and ranking. An inverted index maps terms to the documents containing them.

Use: Product search, article search, or searching logs when text relevance matters.

Example: Keep product records in the relational database and feed changes into a search index. A query returns ranked product IDs or stored document fields.

Limits: Define how updates and deletions reach the index, how stale results are handled, and how to rebuild it. Enforce access controls in search. A derived index is not the authoritative business record.

Compared with a database index: A database index speeds particular queries over its records. A search index adds text analysis and relevance ranking; full-text search can also live inside a relational database.

Related: Inverted index

Message queue

★★★

Accept jobs now; run them later.

Tradeoff: Backlogs and duplicate delivery.

Details
RabbitMQ · Amazon SQS

Use: Move work off the request path

Worker pool → process jobs in parallel
Retry + dead-letter queue → isolate failed jobs

Cost: Duplicate delivery; backlog. Make retries safe.

Related: Queuing

Load balancer

★★★

Spread requests across healthy servers.

Tradeoff: Health checks can lag.

Details
HAProxy · NGINX

Use: Spread requests across services

Health checks → skip unhealthy instances
Round robin → rotate across instances

Cost: Health checks can lag; session affinity can create uneven load.

Object storage and blobs

★★★

Store files; reference them by key.

Tradeoff: Keep file metadata and bytes coordinated.

Details

A blob is a chunk of binary data. Object storage stores data under a key, with metadata; blob storage often names the same category.

Use: Images, videos, backups, and large files.

Example: Store the file as an object; keep its key and ownership in the database.

Cost: Coordinate file and metadata updates; account for upload latency, access controls, and transfer costs.

CDN

★★☆

Serve cached content near users.

Tradeoff: Expiry, invalidation, and origin misses.

Details

A content delivery network serves content through distributed edge locations. The origin remains the source for uncached content.

Use: Images, video, downloads, and cacheable responses. Define cache keys, freshness, invalidation, and access controls; private responses must not leak through shared caches.

Reference: CDN documentation

Key-value store

★★☆

Fetch a value by its key.

Tradeoff: Access paths must fit the key design.

Details

A key-value store retrieves a value using its key. Some products also support ordered keys, indexes, and transactions; those are product-specific features.

Use: Sessions, preferences, and predictable entity lookups. Design keys from access patterns and consider hot keys. A key-value interface alone promises neither consistency nor durability.

Reference: Key-value store documentation

Document store

★★☆

Store an entity as one document.

Tradeoff: Duplication and cross-document updates.

Details

A document store keeps structured records with nested fields and arrays. Fetching an aggregate together can simplify its common read path.

Use: Product catalogs or order-shaped records. Choose embedding versus references based on reads, growth, and updates. Flexible schema still needs validation; indexes and transaction boundaries depend on the store.

Reference: Document store documentation

Publish-subscribe

★★☆

Send one event to many subscribers.

Tradeoff: Each subscriber needs a failure policy.

Details

Publish-subscribe distributes events to multiple subscriptions. This differs from a work queue, where competing workers share jobs.

Use: Several independent reactions to one change. Durability, replay, ordering, and duplicate delivery depend on the transport and configuration. Slow subscribers need buffering and recovery policies.

Reference: Publish-subscribe documentation

Event log

★★☆

Retain events for independent replay.

Tradeoff: Retention, ordering, and reader lag.

Details

An event log retains an ordered sequence that consumers read using their own positions. A partitioned log normally orders events within each partition, not globally.

Use: Replayable pipelines, analytics, and derived views. Retention limits replay; track lag, schema evolution, and duplicate effects. A retained log can support publish-subscribe with durable independent readers.

Reference: Event log documentation

Connection pool

★☆☆

Reuse a bounded set of connections.

Tradeoff: Pool exhaustion makes requests wait or fail.

Details

A connection pool keeps reusable connections ready. Each operation borrows a connection and returns it after use, avoiding repeated connection setup.

Use: Database clients or other services with expensive connection setup and finite connection capacity.

Example: A service reuses a small pool rather than creating a new database connection per request. Wait for a free connection only within an acquisition timeout.

Limits: Budget connections across all service instances. Larger pools can overload the database. Return connections on success and failure; manage idle expiry, broken connections, and transaction or session state.

During a transaction: Keep operations on the same connection until commit or rollback. Pooling reduces setup overhead; it does not increase the database’s processing capacity.

Time-series database

★☆☆

Store measurements over time.

Tradeoff: Retention and label count drive cost.

Details

Stores measurements organized by time.

Use: Metrics, sensor readings, and queries over time ranges.

Example: Keep recent readings in detail; summarize older readings.

Cost: Retention, high-cardinality labels, and late data affect storage and query cost.

Durable execution engine

★☆☆

Run workflows with recorded progress.

Tradeoff: Extra runtime; external actions need safe retries.

Details

Infrastructure that records workflow progress and resumes work after a crash.

Use: Long-running jobs with multiple steps, timers, and retries.

Example: Resume an order workflow at shipping after payment completes.

Cost: Adds a runtime and history storage. Retried external actions still need idempotency; replay rules depend on the engine.

Related: Durable execution

2. Correctness and recovery

Keep results correct when requests repeat or work stops halfway.

Idempotency

★★★

Repeat a request without repeating its effect.

Tradeoff: Request keys need atomic handling and expiry.

Details

Repeating the same logical operation has the same effect as performing it once.

Use: A client may retry after an uncertain response.

Example: Use a request key and an atomic stored result so retrying a payment does not charge twice.

Cost: Define key scope and expiry; reject a reused key with different inputs. A timeout does not prove the action failed.

Transactions

★★★

Commit related changes together.

Tradeoff: Isolation and contention need care.

Details

A transaction groups operations into one commit or rollback boundary. Atomicity prevents partial completion; isolation defines how concurrent transactions interact.

Use: Related updates that must preserve an invariant. Pick appropriate isolation or explicit locking and handle transaction retries. A database transaction does not automatically include an external payment or message send.

Reference: Transactions documentation

Strong consistency

★★★

Read the latest completed write.

Tradeoff: Coordination costs latency and availability.

Details

Define a guarantee that reads see the latest completed write within the stated scope. For a single value, this is often linearizability.

Use: Stale decisions would break correctness.

Example: Read an inventory count and change it with an atomic conditional update; a fresh read alone cannot prevent overselling.

Cost: Coordination can increase latency or require rejecting operations during a network partition. State the exact guarantee and boundary.

Eventual consistency

★★★

Let copies catch up over time.

Tradeoff: Reads may be stale; resolve conflicts.

Details

Copies or derived views converge after updates stop, assuming updates are delivered and conflicts are resolved.

Use: Temporary staleness is acceptable.

Example: Update a profile now; let its search index catch up later.

Cost: Reads can be stale or reordered. Define conflict resolution and how users observe pending updates; eventual does not promise a fixed delay.

Deduplication

★★☆

Skip events already processed.

Tradeoff: Record IDs atomically with effects.

Details

Recognize previously seen requests or events and suppress duplicate processing.

Use: A queue or producer can deliver the same event again.

Example: Record an event ID atomically with its database update.

Cost: Needs durable IDs and retention rules. Recording an ID separately from an external effect leaves a crash gap.

Transactional outbox

★★☆

Commit data and its outgoing event together.

Tradeoff: Publishing can repeat; consumers need safe handling.

Details

Write business data and an outgoing event in one database transaction; a relay publishes the event later.

Use: A database update must reliably lead to a message.

Example: Commit an order and its “order created” event together; publish pending outbox rows.

Cost: Relay lag and cleanup. Publishing can repeat, so consumers still need deduplication or idempotency.

Optimistic locking

★★☆

Update only if the record has not changed.

Tradeoff: Conflicts require retry or user resolution.

Details

Read a record and its version. Update it with one atomic condition: the stored version must still match. Increment the version on success; a failed condition means another writer changed the record.

Use: Prevent lost updates when conflicts are infrequent.

Example: Two editors read version 7. The first writes version 8; the second update expecting version 7 fails instead of overwriting it.

Limits: Reload and recompute or ask the user to resolve a conflict. Bound retries under contention. A separate check followed by an unconditional write is unsafe; protecting one record does not enforce every multi-record invariant.

Conditional updates

★★☆

Change state only if a condition holds.

Tradeoff: Conflicts need a deliberate response.

Details

A conditional update atomically tests a predicate and applies a write. The check and write must happen as one storage operation; checking first in application code leaves a race.

Use: Seat claims, inventory decrements, and compare-and-set. Optimistic locking is a version-based form. Define what happens on failure and use a transaction for invariants spanning multiple records.

Reference: Conditional updates documentation

Durable execution

★☆☆

Resume work after a crash.

Tradeoff: Unrecorded external effects may repeat.

Details

Persist progress so a workflow can recover instead of starting from scratch.

Use: Work must survive crashes or wait for hours or days.

Example: Record completed steps and durable timers; resume the remaining work after restart.

Cost: Recovery storage and workflow versioning. A remote action may succeed before its completion is recorded; make retries safe.

Related: Durable execution engine

References: Transactional outbox · Durable execution

3. Traffic and overload

Control arrival rate, waiting work, and failure amplification.

Rate limiting

★★★

Cap incoming work over time.

Tradeoff: Choose fair limits and burst rules.

Details

Limit how much work a caller can submit over time.

Use: Protect quotas, fairness, or a dependency’s request budget.

Example: Use a token bucket to allow short bursts while limiting the sustained rate.

Cost: Choose keys and burst rules. Distributed counters add coordination or approximation; explain retry timing to callers.

Queuing

★★★

Buffer bursts for later processing.

Tradeoff: Waiting grows under sustained overload.

Details

Buffer accepted work so consumers can process it later.

Use: Smooth a temporary burst or move work off the request path.

Example: Accept a report job and return its ID while a worker processes it.

Cost: Adds wait time and duplicate-delivery concerns. Bound capacity and expiry; a queue cannot fix sustained overload.

Related: Message queue

Retry mechanisms

★★★

Try temporary failures again.

Tradeoff: Bound retries; avoid duplicate effects.

Details

Repeat an operation when a temporary failure is likely to clear.

Use: Transient network errors, throttling, or temporary dependency outages.

Example: Use exponential backoff with jitter, honor retry guidance, and cap attempts within a deadline.

Cost: Retries amplify load. Retry only eligible errors and safe operations; avoid retries at every layer and isolate terminal failures.

Timeouts and circuit breakers

★★★

Stop waiting; stop calls to failing services.

Tradeoff: Timed-out actions may still succeed.

Details

A timeout bounds one wait; a circuit breaker temporarily stops calls to a failing dependency.

Use: Slow or failing services threaten the caller’s capacity.

Example: Apply an overall deadline; open the breaker after repeated failures and probe for recovery.

Cost: Timeouts leave outcomes uncertain. Breakers can reject work during recovery; define fallback and safe retry behavior.

Backpressure

★★☆

Ask producers to slow down.

Tradeoff: Producers must cooperate.

Details

Tell upstream producers to slow down when downstream capacity is exhausted.

Use: Prevent buffers and in-flight work from growing without bound.

Example: Pause consumption or reduce producer concurrency when workers reach their limit.

Cost: Propagates delay upstream; requires cooperative producers and bounded buffers. Size limits protect the boundary when producers cannot slow down.

Load shedding

★★☆

Reject excess work to preserve capacity.

Tradeoff: Some requests fail or data is dropped.

Details

Reject or drop some work when capacity is exhausted.

Use: Preserve useful service during overload.

Example: Reject low-priority requests before expensive processing while reserving capacity for critical work.

Cost: Some requests fail or data is dropped. Define priority, fairness, and which accepted work must be preserved.

Dead-letter queue

★★☆

Isolate jobs that cannot be processed.

Tradeoff: Needs monitoring, retention, and safe replay.

Details

A separate queue holds messages that fail processing according to a configured policy, such as exhausting a delivery-attempt budget. Successful jobs continue through the main queue.

Use: Repeatedly failing messages need investigation without unlimited retries.

Recovery: Alert on arrivals and age, retain the failure context, fix the cause, then replay at a controlled rate. Consumers still need idempotency or deduplication.

Limits: Moving a message aside can break strict processing order. Unmonitored messages may expire; a DLQ isolates failure but does not fix it. Delivery-count and retention rules depend on the queue implementation.

Reference: Amazon SQS dead-letter queues

Reference: Throttling and load control

4. Data access and scale

Change how data is found, divided, and copied.

Indexing

★★★

Find rows without scanning everything.

Tradeoff: Extra storage and write work.

Details

Maintain an extra lookup structure for selected fields. A B-tree keeps sorted keys in pages: follow the key ranges to a leaf, then use its row reference. This simplified diagram searches for 20 and fetches Row 2; a real page contains many keys.

Use: Queries scan too many records.

Example: Index a short-link code for lookup, or an account ID plus timestamp for recent events.

Cost: Extra storage and write work. Index types differ: hash indexes suit equality lookups, while B-trees also support ranges. Column order and query shape matter; measure the query plan.

Partitioning

★★★

Split a dataset into manageable pieces.

Tradeoff: Poor keys create hot partitions.

Details

Split a dataset into smaller pieces by range, hash, or another rule.

Use: Prune scans or manage chunks of data independently.

Example: Partition measurements by time so old data can be removed as a unit.

Cost: Poor keys create hot partitions. Partitioning can remain inside one database server; it does not automatically add machines.

Sharding

★★★

Spread data across database servers.

Tradeoff: Cross-shard work and rebalancing get harder.

Details

Place subsets of data on different database servers.

Use: One server cannot handle the dataset or workload.

Example: Hash account IDs across shards; route each account’s requests to its shard.

Cost: Hot keys, resharding, cross-shard queries, and transactions become harder. Choose the key from access patterns.

Read replication

★★★

Serve reads from database copies.

Tradeoff: Replicas may lag.

Details

Maintain database copies to serve reads or support failover.

Use: Read traffic exceeds the primary’s capacity.

Example: Send staleness-tolerant reads to replicas and freshness-sensitive reads to the authoritative path.

Cost: Asynchronous replicas may lag. Failover and consistency guarantees depend on the replication design.

Caching strategies

★★★

Load on a miss; reuse the result.

Tradeoff: Invalidation and expiry need care.

Details

Keep reusable results close to readers and define how they become stale.

Use: Repeated reads are expensive.

Example: Cache-aside reads the database on a miss; expire or invalidate cached entries when data changes.

Cost: Stale values, invalidation races, and bursts of misses. Use request coalescing or staggered expiry when needed.

Related: Cache

Inverted index

★★☆

Map words to the documents containing them.

Tradeoff: Extra storage and updates as documents change.

Details

An inverted index, sometimes called a reverse index, maps each searchable term to a list of matching document IDs. That list is called a postings list. It reverses the usual document-to-words relationship.

Example: Document 1 contains “cat”; document 2 contains “dog”; document 3 contains both. Intersect their postings lists for an AND query to return document 3. Union them for an OR query to return documents 1, 2, and 3.

Related to Search index: An inverted index is a data structure commonly used inside a search index. The broader search system handles document ingestion, text analysis, query execution, filtering, and ranking.

Limits: Apply compatible text analysis to documents and queries, including tokenization and case handling. Update postings on edits and deletions. Phrase matching needs positions; relevance ranking can use term frequencies and other signals. Simple term membership alone provides neither.

Related: Search index

Consistent hashing

★★☆

Change nodes; remap only part of the keys.

Tradeoff: Uneven load and data migration still need care.

Details

Hash keys and nodes into the same space. In a ring implementation, assign each key to the next node clockwise. Adding a node takes over a neighboring range; removing one sends its range to the next owner.

Which hash? Consistent hashing is a placement scheme, not one required hash algorithm. Use a deterministic hash with a uniform spread, such as xxHash64 or MurmurHash; all routers must agree on the algorithm, seed, encoding, and membership. Hash both keys and node/virtual-node IDs into the same fixed space.

Why not modulo? Direct placement uses hash(key) % N, where N is the server count, not a server ID. Changing N changes most assignments: hash 10 maps to bucket 1 with 3 servers, but bucket 2 with 4. A ring keeps existing node positions fixed and moves only the range owned by the added or removed node. Modulo is fine for a stable bucket count; fixed logical buckets can also separate placement from physical servers.

Use: Cache clusters, shard routing, or request affinity when membership changes.

Example: Adding C moves nearby keys from B to C while the other ranges keep their owners. The diagram shows one position per node; virtual nodes give each physical node multiple positions to improve balance.

Limits: Hot keys can still overload a node. Clients need a consistent membership view; routing alone does not copy data, provide replication, or guarantee strong consistency.

Reference: Envoy ring hash · Hash function options

Change data capture

★★☆

Feed committed data changes to other systems.

Tradeoff: Lag, replay, and schema changes need care.

Details

Change data capture (CDC) detects committed inserts, updates, and deletes and exposes them to downstream consumers. Log-based CDC reads the database’s change log; other approaches use triggers or polling.

Use: Update a search index, analytics store, or cache from database changes.

Example: A product update commits in the database; CDC forwards the change to the search index. Track source positions so processing can resume after failure.

Limits: Handle duplicates, deletes, schema evolution, and the transition from an initial snapshot to live changes. Lag and log retention affect recovery; ordering guarantees depend on the source and pipeline.

With an outbox: CDC can publish committed outbox records. Raw row changes and business events express different meanings; choose the contract consumers need.

Batching

★★☆

Group operations to reduce per-call overhead.

Tradeoff: Waiting adds latency; partial failures need handling.

Details

Collect several operations and submit them together. Flush when the batch reaches a size or byte limit, or when a short timer expires.

Use: Bulk writes, network requests, or queue acknowledgments when per-operation overhead is significant.

Example: Send several search-index updates in one request rather than opening a request for every document.

Limits: Bound memory and payload size. Inspect individual results and safely retry failed items. A batch is not automatically atomic or ordered; those guarantees depend on the API.

Compared with batch processing: Batching groups operations within a live flow. Batch processing runs accumulated datasets as a job; either approach can use batches internally.

Denormalization

★★☆

Copy data to simplify common reads.

Tradeoff: Copies need coordinated updates.

Details

Denormalization duplicates selected data to avoid joins or assemble common reads cheaply. Start from the query that needs improvement.

Use: Read-heavy feeds, catalogs, and query-shaped records. Specify the authoritative record, update propagation, stale-copy tolerance, and repair process. Copies make reads easier and writes more complicated.

Reference: Denormalization documentation

Materialized views

★★☆

Store the result of a useful query.

Tradeoff: Refresh cost and freshness lag.

Details

A materialized view stores a query result, such as totals by day. Refreshing it updates the stored result; this differs from an ordinary view that executes its query when read.

Use: Repeated expensive joins or aggregates. Choose full refresh or an appropriate incremental pipeline, and state the freshness guarantee. Refresh and concurrent-read behavior depend on the database.

Reference: Materialized views documentation

5. Regions and processing

Choose where requests run and when data is processed.

Multi-data-center deployment

★★☆

Run the application in separate failure domains.

Tradeoff: Replication, failover, and extra capacity cost.

Details

Deploy a regional application stack in more than one data center or region. Keep enough dependencies available in the surviving region so traffic can continue after an outage.

Active-active: Multiple regions serve traffic. Define write ownership, conflict handling, and acceptable data lag.

Active-passive: A standby takes over. Define promotion, traffic switching, and how the old primary is prevented from continuing to write.

Recovery: Choose how much data loss and downtime are acceptable, test failover and failback, and reserve capacity. Replication alone is not a recovery plan.

Boundaries: Availability zones within one region and geographically separate regions address different failure scopes. This diagram shows logical regional stacks; a region can contain multiple data centers.

Regional MySQL + Redis

★★☆

Serve common reads locally; choose database coordination per operation.

Tradeoff: Local latency versus coordination, conflicts, and stale caches.

Consistency and applications

How it works: each regional API uses Redis for common reads and sends writes to MySQL. On a cache miss, read the database and populate Redis. Writable database members replicate changes; caches need their own invalidation or refresh policy.

Two different replication designs: independent MySQL primaries with asynchronous replication can acknowledge local writes before other regions receive them. They need explicit write ownership or conflict resolution; concurrent writes can diverge. MySQL Group Replication instead coordinates transaction ordering and conflict certification through a group. Its EVENTUAL setting permits lagging reads, but does not mean each isolated region can keep accepting writes without a quorum.

MySQL consistency settings: in Group Replication, BEFORE waits for preceding transactions to apply locally before execution. AFTER waits for a read-write transaction’s changes to apply on the other group members before it completes. BEFORE_AND_AFTER combines these behaviors. These settings operate within that replication protocol; asynchronous replication has no equivalent consistency switch. Multi-primary Group Replication does not support SERIALIZABLE isolation by default.

Reads through Redis: even after database replication completes, a cached value can be stale. TTL bounds entry lifetime, not replication lag or stale refills. Invalidation must reach every region, and a concurrent cache fill can race with invalidation. For correctness-sensitive reads, bypass Redis and use the database’s required consistency barrier and isolation. For read-your-writes, route to an up-to-date database or wait for the write’s position before reading; this is a narrower guarantee than global strong consistency.

Apply it: URL-shortener redirects, public profiles, and product descriptions can often tolerate short-lived stale reads. Define how quickly edits and deletions must become visible. Seat reservations, inventory decrements, and permission revocations need authoritative decisions: route conflicting writes to one owner or use a coordinated database protocol with transactions or conditional updates that enforce the invariant. Keep cached displays separate from the final correctness check.

Latency and failures: coordination across regions adds network latency. Waiting for every member also makes a slow member part of the response path. During a partition, a coordinated group needs quorum; unsafe minority writes must be refused. If every region must keep writing independently, accept weaker guarantees and define reconciliation. Plan membership changes, retries with idempotency, failover, and cache recovery.

Reusable interview framework: state the invariant and permitted staleness first, then choose write ownership, replication protocol, read path, cache policy, and partition behavior. The regional topology is reusable; its guarantees must be selected per operation.

References: MySQL consistency guarantees · Multi-primary limitations

Kubernetes across regions

★☆☆

Run application workloads in each regional cluster.

Tradeoff: Cluster operations and regional configuration drift.

Details

A common Kubernetes design uses an independent cluster per region, with nodes spread across availability zones inside that region. Deploy the application services and background workers into each cluster.

What Kubernetes does: Schedules container workloads, replaces failed pods, exposes services, and manages rollouts. Configured autoscaling can adjust workload replicas; node capacity needs its own management.

Regional stack: Global DNS selects a regional endpoint; a regional load balancer or ingress sends requests to services and pods.

Infrastructure: Provision networks, machines, load balancers, storage, and managed databases through cloud infrastructure tooling or a managed platform. Kubernetes can run stateful workloads too, but cross-region data replication and recovery require explicit design.

Limits: Kubernetes is an option, not a prerequisite for multiple regions. It does not automatically provide global routing or data consistency. Keep secrets, versions, observability, and rollout policies coordinated across clusters.

Reference: Kubernetes across failure zones

GeoDNS

★☆☆

Return a regional address based on user location.

Tradeoff: Location estimates and cached answers can delay rerouting.

Details

Use: serve users closer to home and survive a regional outage.

Routing path: On a cache miss, the resolver asks authoritative DNS. GeoDNS returns a regional endpoint address using the resolver location or client subnet. The client then connects to that endpoint’s load balancer and application.

Policy: Configure region mappings, a default answer, and health-aware failover. Location-based routing chooses by geography; latency-based routing chooses using latency measurements.

Dashed blue: DNS lookup + answer. Solid green: application request.

DNS chooses an address. The user connects directly to that data center; traffic does not pass through DNS.

Cost: cross-region data lag, write conflicts, and higher cost. Add health-aware failover; cached DNS answers delay changes.
Nearby ≠ fastest: location comes from the resolver or client subnet. Use latency-based routing when latency is the goal.

References: Geographic routing · Location estimation

Batch vs. stream processing

Batch processing

★★☆

Process accumulated data on a schedule.

Tradeoff: Results wait for the next run.

Details
Scheduled jobs · Spark · HDFS

Use: yesterday’s report or a large historical backfill.

HDFS: distributed file storage, not the processing engine.
Cost: results wait for the next run.

Stream processing

★★☆

Process events as they arrive.

Tradeoff: Late events, state, and recovery add complexity.

Details
Kafka → Flink → output

Use: live counts, alerts, or continuously updated views.

Patterns: windows, keyed state, joins, and event sequences.
Cost: late events, state size, and recovery complexity.

Exactly-once recovery

★☆☆

Replay work without duplicating its effect.

Requires: Compatible source, checkpoints, and sink.

Guarantees and limits
Exactly-once: one effect, even after replay.

Flink checkpoints operator state + source positions. After failure, restore and replay; events may run again, but recovered state reflects each event once.

End to end: enable exactly-once checkpointing, use a replayable source such as Kafka, and a compatible transactional or correctly deduplicating sink. External effects need the same care.

Checkpoint → failure → restore → replay → no duplicate effect

6. Live delivery

Choose how clients receive new information.

Polling

★★☆

Ask periodically for new data.

Tradeoff: Repeated calls and delayed updates.

Details

Clients make repeated HTTP requests. Each colored pair is a separate request and completed response, rather than one continuous stream. The underlying TCP connection may be reused through HTTP keep-alive or HTTP/2; a new connection per poll is optional, not required. Choose an interval based on acceptable delay and traffic. Long polling instead holds a request until an update or timeout, then reconnects; either needs retries and a cursor if missed events matter.

Reference: Polling documentation

Server-sent events

★★☆

Push updates from server to client.

Tradeoff: Reconnect and replay need a policy.

Details

An HTTP response streams server-to-client events. Client commands can use separate HTTP requests. Use event IDs and retained history when reconnection must resume missed events; an open connection alone provides no durable delivery guarantee.

Reference: Server-sent events documentation

WebSockets

★★☆

Exchange messages in both directions.

Tradeoff: Connection state and flow control.

Details

A persistent connection supports bidirectional messages. Use for chat or collaboration when both sides exchange frequent updates. Plan connection routing, reconnects, authentication, heartbeats, and bounded buffers. WebSocket transport alone does not supply replay or exactly-once effects.

Reference: WebSockets documentation

7. Apache Flink patterns

Choose the question first: separate reporting buckets, a rolling metric, a visit, per-entity memory, related events, or an event sequence. A common path is Kafka → Flink → an analytics store, serving view, or alert topic.

Time and late events: event time uses the timestamp of the event; processing time uses the worker’s clock. A watermark expresses progress in event time, not a guarantee that every event has arrived. Decide how much delay to tolerate and whether late data updates results, goes to a side output, or is dropped. Watermark stalls delay event-time windows and timers.

Interview checklist: name the key, window size or deadline, acceptable result delay, state retention, and correction policy. Explain checkpoint recovery and the sink’s guarantees using exactly-once recovery.

Tumbling window

★★☆

Summarize separate, fixed time buckets.

Tradeoff: Results wait for the bucket to close.

Applications and tradeoffs

How it works: Group events into non-overlapping intervals. A five-minute window covers [12:00, 12:05), then [12:05, 12:10). An event at 12:05 belongs to the second bucket. Key by the entity whose totals you need, such as URL, merchant, or service.

Apply it: URL-shortener analytics: count clicks per URL every five minutes. Monitoring: calculate requests and errors per service per minute. These are independent reporting buckets.

Design decisions: Use incremental counts or sums rather than retaining every event. Event-time output depends on watermark progress; late corrections require a sink that can update the same bucket.

Sliding window

★★☆

Refresh a recent-history aggregate at a fixed cadence.

Tradeoff: Overlapping windows increase work and state.

Applications and tradeoffs

How it works: Define both a window size and a slide. A ten-minute window sliding every minute answers “what happened in the last ten minutes?” once a minute. With this configuration, one event contributes to ten overlapping windows.

Apply it: Trending feed: rank posts by recent engagement, refreshing every minute. Abuse monitoring: alert on a user’s failed logins over the last ten minutes. Combine per-key aggregation with ranking or alert logic.

Design decisions: The slide sets refresh frequency, not per-event output. Plan state size, late corrections, and hot keys. An asynchronous Flink alert cannot enforce a synchronous API rate limit; use an atomic check on the request path for admission.

Session window

★★☆

Group bursts of activity separated by inactivity.

Tradeoff: Late events can merge earlier sessions.

Applications and tradeoffs

How it works: Choose an inactivity gap per key. With a thirty-minute gap, a user’s events remain in one session while consecutive events are less than thirty minutes apart. A longer gap starts another session; there is no fixed clock-aligned duration.

Apply it: Clickstream analytics: group page views into visits and measure session duration or conversion. Shopping analytics: group browsing and cart actions into journeys. This is an analytical session, separate from an authentication session.

Design decisions: An event-time session closes when the watermark passes its end. If retained for allowed lateness, a late event can bridge and merge sessions. Design correction handling and bound how much session state you retain.

Keyed state and timers

★★☆

Remember per-entity history between events.

Tradeoff: Retention and hot keys govern state growth.

Applications and tradeoffs

How it works: Partition events by an entity key and keep managed state for that key. Update a running total, remember a seen event ID, or register a timer for a deadline. State is recovered from checkpoints; it is more than an in-memory variable.

Apply it: Notification pipeline: suppress duplicate event IDs during a defined retention period. Order monitoring: emit an alert if payment has not arrived by a deadline. Live dashboards: maintain per-merchant running totals.

Design decisions: Set retention from the replay and duplicate horizon; once a seen ID expires, the duplicate can pass again. Event-time timers require watermark progress. External notifications still need an idempotent or transactional delivery path.

Interval join

★★☆

Match related events within a bounded time range.

Tradeoff: Buffering both streams costs memory and adds delay.

Applications and tradeoffs

How it works: Join two keyed streams using their event timestamps and a bounded interval. For example, match an impression with clicks that occur from zero to five minutes afterward, using a shared impression ID.

Apply it: Ad analytics: attribute a click to its impression. Order analytics: correlate an order with payment events within the chosen business interval. Write matched results to an analytics store or downstream topic.

Design decisions: Watermarks allow old buffered events to be removed. Choose a bound that includes expected business delay and define how late or unmatched events are handled. Multiple matches can produce multiple rows; aggregation or deduplication may be needed. Correlation alone does not enforce payment correctness.

Event-sequence detection (CEP)

★★☆

Detect an ordered pattern across multiple events.

Tradeoff: Partial matches and ordering rules add state.

Applications and tradeoffs

How it works: Complex event processing (CEP) detects sequences with conditions and a time bound. For example, detect repeated failed logins followed by a successful login from a new device within ten minutes. Define whether intervening events are allowed.

Apply it: Fraud detection: suspicious login then unusual purchase. Operational monitoring: repeated sensor warnings then a shutdown. Produce a risk signal or alert for another service to act on.

Design decisions: Bound the match duration and decide whether overlapping matches should produce repeated alerts. Event-time ordering depends on watermarks; choose a late-event policy. An alert is a signal, so any resulting block or notification needs its own reliable execution path.
